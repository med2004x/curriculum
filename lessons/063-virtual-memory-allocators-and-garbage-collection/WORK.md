## 3. Guided practice

4. Predict what a warm file cache might change on a second read.

Run the smallest case first. Record prediction and observation side by side.

### Practice B — Modify one variable

### Practice C — Guided instrumentation

## 4. Independent exercises

### Exercise 1 — Recall and prediction
Without running anything, explain the main mechanism in **Interpret selected regions and permissions in `/proc/<pid>/maps`.**. Predict the result for one ordinary input and one boundary input. Record both predictions before checking them.

### Exercise 2 — Guided-to-independent implementation
Rebuild the smallest useful version of the lesson's main mechanism from a blank file. Your implementation must satisfy **Distinguish virtual mapping, resident pages, minor faults, and major faults.**. Start with a written data/control-flow sketch, then code, then verify.

### Exercise 3 — Debug and repair
Take your implementation and introduce one realistic defect: wrong boundary, wrong state update, missing cleanup, incorrect error branch, or invalid assumption. Reproduce the failure, classify it, fix it, and add a regression test or evidence step.

### Exercise 4 — Transfer
Change one important constraint from the lesson. Examples: larger input, partial failure, concurrent callers, invalid data, persistence, or a different representation. Explain which invariant survives, which one changes, and why.

### Exercise 5 — Explanation

## 5. Problem-solving lab

Model the resource, owner, state transitions, and failure path explicitly. Solve a small concrete case before implementing the general mechanism.

### Problem-solving protocol

1. Restate the problem and constraints.
2. Produce a small concrete example.
3. State the invariant or contract.
4. Write the simplest baseline solution or model.
5. Identify the bottleneck, failure, or repeated work.
6. Improve it only after you can explain the baseline.
7. Verify against a case designed to break the naive solution.

## 6. Coding challenge

### Allocator experiment

Build a simple allocator model or instrument allocation patterns, then compare fragmentation and lifetime behavior with garbage-collected allocation.

### Acceptance criteria

- The main path works on normal input.
- At least two boundary or invalid cases are tested.
- One failure mode is deliberately reproduced and then fixed.
- The implementation can be explained from a blank page in terms of state and invariants.
- Verification is reproducible from commands recorded in your evidence file.

## 8. Debugging and failure lab

1. Rerun step 3's file-reading test a second time, immediately after the first run, without doing anything to clear caches in between.

2. Observe the major fault count drop sharply (likely to near zero) on the second run.

3. Explain why: the OS's page cache now holds the file's contents in RAM from the first read, so the second read's page faults are resolved as *minor* faults (the data's already in memory, just needs mapping into this process) rather than major faults requiring an actual disk read — this is the same mechanism that makes "warm cache" reads of recently-accessed f.

4. Reproduce the failure from a clean terminal session and write the smallest change that returns the system to the expected contract.

Rule: never fix a failure by changing multiple unrelated things at once. The objective is diagnosis, not ritual.

## 9. Transfer and design reasoning

Change one memory-pressure condition: change working-set size, retain versus release references in Go, or read a previously cached file. Explain which metric should change and which allocator/runtime policy may obscure it.

Your transfer answer is complete only when the changed constraint is explicit and the evidence distinguishes the new case from the original case.

Then answer: **What would make your current solution wrong even though all visible examples still pass?**
