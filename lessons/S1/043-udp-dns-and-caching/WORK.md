## 3. Guided practice

### Practice A — Predict
1. Predict what UDP does if a datagram is lost or reordered.
2. Predict the difference between querying A and AAAA records.
3. Predict the response distinction between `NXDOMAIN` and an empty successful answer.
4. Predict what a timeout tells you and what it does not tell you about name existence.
5. Predict how a cached TTL may change across repeated queries.
6. Predict why two resolvers may return different valid address sets.
7. Predict why DNS may use TCP after a truncated UDP response.
8. State which transport guarantee comes from UDP and which behavior belongs to DNS/client policy.

Run the smallest case first. Record prediction and observation side by side.

### Practice B — Modify one variable
Take the smallest runnable example from the lecture and change exactly one thing. Do not add new concepts yet. Predict the change, run it, and explain the delta in one paragraph.

### Practice C — Guided instrumentation
Instrument one internal state: an index, pointer, counter, transaction state, request ID, queue length, timestamp, or equivalent. The instrumentation must let you answer “what changed?” rather than merely “did it work?”

## 4. Independent exercises

### Exercise 1 — Recall and prediction
Without running anything, explain the main mechanism in **Explain UDP datagrams and what UDP does not guarantee.**. Predict the result for one ordinary input and one boundary input. Record both predictions before checking them.

### Exercise 2 — Guided-to-independent implementation
Rebuild the smallest useful version of the lesson's main mechanism from a blank file. Your implementation must satisfy **Read a DNS question and response for record type, answer, TTL, and response code.**. Start with a written data/control-flow sketch, then code, then verify.

### Exercise 3 — Debug and repair
Take your implementation and introduce one realistic defect: wrong boundary, wrong state update, missing cleanup, incorrect error branch, or invalid assumption. Reproduce the failure, classify it, fix it, and add a regression test or evidence step.

### Exercise 4 — Transfer
Change one important constraint from the lesson. Examples: larger input, partial failure, concurrent callers, invalid data, persistence, or a different representation. Explain which invariant survives, which one changes, and why.

### Exercise 5 — Explanation
Write a 150–250 word technical explanation of **Distinguish a DNS negative answer from a timeout or transport failure.** as if another student must implement it from your explanation. No screenshots; the explanation must stand on its own.

## 5. Problem-solving lab

Given a client/server trace with missing, delayed, or duplicated messages, reconstruct the state transitions and identify the first point where the application can no longer infer the desired state.

### Problem-solving protocol

1. Restate the problem and constraints.
2. Produce a small concrete example.
3. State the invariant or contract.
4. Write the simplest baseline solution or model.
5. Identify the bottleneck, failure, or repeated work.
6. Improve it only after you can explain the baseline.
7. Verify against a case designed to break the naive solution.

## 6. Coding challenge

### UDP + DNS probe

Write a Go diagnostic tool that sends a bounded UDP request or performs DNS lookups, records timing, and handles loss or timeout explicitly.

### Acceptance criteria

- The main path works on normal input.
- At least two boundary or invalid cases are tested.
- One failure mode is deliberately reproduced and then fixed.
- The implementation can be explained from a blank page in terms of state and invariants.
- Verification is reproducible from commands recorded in your evidence file.

## 8. Debugging and failure lab

1. Modify your step 3 client to query a domain that doesn't exist (e.g. a deliberately made-up subdomain), and observe the response's flags/response-code field (an `NXDOMAIN` response, encoded in the DNS response header) rather than a valid IP address.

2. Parse this response code explicitly in your client and confirm you can distinguish "this domain doesn't exist" from "no response arrived" (a timeout) and from "a valid IP was returned" — three genuinely different outcomes a real DNS client must handle differently, and a common source of bugs in hand-rolled or poorly-tested DNS handling code that only tests t.

3. Remove one verification step and record what evidence is lost.

4. Reproduce the failure from a clean terminal session and write the smallest change that returns the system to the expected contract.

Rule: never fix a failure by changing multiple unrelated things at once. The objective is diagnosis, not ritual.
