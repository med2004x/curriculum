## 3. Guided practice

### Practice A — Predict
1. Predict the result of the smallest lesson-specific case.
2. Predict one boundary case and state exactly which observation would confirm it.
3. Predict the first failure signal if one assumption is broken.
4. Predict which state, file, process, query, or interface is responsible for the observable result.
5. Predict what changes when one constraint is changed and all other inputs stay fixed.
6. Predict the verification command before you run it.
7. Predict one debugging step that would reduce the problem to a smaller case.
8. Write the prediction down before executing any of the cases.

Run the smallest case first. Record prediction and observation side by side.

### Practice B — Modify one variable
Take the smallest runnable example from the lecture and change exactly one thing. Do not add new concepts yet. Predict the change, run it, and explain the delta in one paragraph.

### Practice C — Guided instrumentation
Instrument one internal state: an index, pointer, counter, transaction state, request ID, queue length, timestamp, or equivalent. The instrumentation must let you answer “what changed?” rather than merely “did it work?”

## 5. Problem-solving lab

Given a client/server trace with missing, delayed, or duplicated messages, reconstruct the state transitions and identify the first point where the application can no longer infer the desired state.

### Problem-solving protocol

1. Restate the problem and constraints.
2. Produce a small concrete example.
3. State the invariant or contract.
4. Write the simplest baseline solution or model.
5. Identify the bottleneck, failure, or repeated work.
6. Improve it only after you can explain the baseline.
7. Verify against a case designed to break the naive solution.

## 6. Coding challenge

### TLS client

Write a TLS client diagnostic that verifies certificate properties, records the negotiated protocol, and explains which trust decisions are local versus remote.

### Acceptance criteria

- The main path works on normal input.
- At least two boundary or invalid cases are tested.
- One failure mode is deliberately reproduced and then fixed.
- The implementation can be explained from a blank page in terms of state and invariants.
- Verification is reproducible from commands recorded in your evidence file.

## 8. Debugging and failure lab

1. Take your step 1 self-signed server and, using a packet capture tool (Lesson 7 preview) or a network proxy tool, attempt to read the actual HTTP request/response content passing over your `curl -k` connection at the raw TCP byte level (not through the TLS-aware tool itself, but genuinely at the wire).

2. Confirm the payload is unreadable ciphertext, not plaintext HTTP — directly demonstrating the confidentiality guarantee is real and independent of whether authentication was properly verified in this specific test (since you used `-k` to skip that check).

3. Explain why this is the concrete, hands-on version of the abstract "separable guarantees" point from Learn: your step 1/2 test showed authentication can fail while encryption still works, and this drill shows encryption genuinely works (not just claimed) even in a scenario where you deliberately bypassed authentication.

4. Reproduce the failure from a clean terminal session and write the smallest change that returns the system to the expected contract.

Rule: never fix a failure by changing multiple unrelated things at once. The objective is diagnosis, not ritual.

## 10. Academic drill

1. **Algorithm statement:** Write the input, output, invariant, and termination argument before coding.
2. **Dry run:** Solve one non-trivial example by hand and show each state change.
3. **Complexity:** Give worst-case time and extra-space bounds and justify them.
4. **Transfer:** Change one constraint and explain which part of the algorithm must change.
